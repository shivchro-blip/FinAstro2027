# The 2026 monthly calendar, run as a fixture — the baseline

**166 of 354 printed windows reproduced; 173 of them were claimed by a rule that
can fire, and 166 of those 173 landed.** The first end-to-end test this build has
had. Generated by `tools/monthly_match.py` against `build/astronomy_2026.json`
and `data/source_2026.html`; nothing on this page is typed.

**This is the BASELINE run, before the configuration port is wired.** `verdicts.py`
fires catalogue B alone. The 38 groups ported in part 1 live in their own registry
and reach no calendar row, so every row here that only a configuration group states
is counted as a **wiring** gap and named as one. The same fixture is re-run after
the wiring and the two results diffed; that diff, not this page, is what the port
is worth.

**The post-wire numbers are 168 of 354 and 168 of 175**, and they are recorded in
`build/NEXT_SESSION.md` and in `conventions.yaml -> verdict_coverage.two_denominators`,
which is what `build/calendar_2027.html`'s apparatus panel reads. This page stays at
166 on purpose: it is the baseline the diff is measured from, and a baseline that
gets updated is not one.

Nothing was tuned. No tolerance was widened to improve a number. The run found **no
new defect in a rule**: it measured one declared limitation against the document
for the first time, identified two further source defects, and left exactly one
near-miss without a cause. All of that is recorded below rather than acted on,
because changing the layer inside the measurement would make the measurement
meaningless.

## What was validated in isolation, and what had never been validated at all

Every convention in this build was checked against the source one table at a time:
the ayanamsha against printed ingress instants, the weekday rule against 75 dated
rows under four competing readings, the tithi and yoga edges against 36 and 14
printed times, the civil-day overlap against 13 tables, the speed levels against
the printed Fast/Normal boundaries, Shar, the dignity frames. **All of it tested
parts.** Chapter 4 is the source's own finished output — twelve month blocks, each
row a dated window with the document's own inference — and until this run nothing
had ever asked whether the assembled layer reproduces it.

## The fixture

Read out of the document at call time by `finastro/monthly2026.py`, exactly as
`cfgsections.py` reads the configuration blocks. Not one date, time or inference
is transcribed: a hand-copied fixture is a second copy of the document that can
drift from it, and a comparison against a drifted copy measures the transcription.

| | count | what it is |
| --- | --- | --- |
| printed rows | **407** | what the twelve tables contain |
| distinct dated windows | **354** | after the carry-overs are folded |
| carry-over copies | **53** | a window spanning a month boundary is reprinted in each month it touches — the Rahu Vedh of 01-Jan to 02-Aug appears in **seven** blocks |
| distinct event names | **147** | how many kinds of thing are printed |
| instants / spans | **136 / 218** | a row with no end date against one with both |
| windows whose inference VARIES between months | **2** | see below |

**354 is the denominator, not 407.** A rate over 407 would count one window up to
seven times and would move if the document's page breaks moved.

**Two windows are reprinted with a different inference.** The Capricorn stellium
(17-Jan → 03-Feb) is *Explained separately* in January and *Positive for Sectors
ruled by Rahu* in February; `Saturn Vehda of Ardra` (25-Jan → 17-May) is *Positive
for Sectors ruled by Rahu* in January and *Explained separately* in February. The
fold key is therefore the window and **not** the inference, and both variants are
carried on the row. Which of two printed inferences is "the" inference of a window
is the document's question, not ours.

## Which rule claims which row — and why that list is hand-written

`finastro/monthlymap.py` assigns each of the 147 event names to the rules that
claim it. It is written by hand, against the catalogue-B section titles and the 58
configuration groups, and **nothing is matched by string similarity**.

That is §12.16 applied. If "which rule should have fired here" were answered by the
same registry whose behaviour is being measured, every row would match by
construction and the check could not fail. The map is checked in both directions on
every run: **147 of 147 names assigned, 0 unmapped, 0 stale, and every rule id it
names exists in a registry.** A name the document prints that the map does not
carry is a hard failure of the matcher, not a silent zero.

| assignment | names | meaning |
| --- | --- | --- |
| `B` | **130** | one or more catalogue-B rules claim it |
| `NO_SECTION` | **9** | no section anywhere, and no series either |
| `SERIES_NO_RULE` | **4** | the astronomy layer emits the series; no rule states a condition on it |
| `CFG` | **2** | a configuration group claims it, and that group is not wired |
| `SUBTABLE` | **2** | one of the nine `<h2>` sub-tables outside the 58 |

## The run

`build/astronomy_2026.json` — 4,167 records — is generated by
`tools/build_2026.py`, which is `build_2027.py` with the year set to 2026 before
`finastro.events` is imported. Not a second engine: the only differences between
the two runs are the year and the output path. The rule layer then reads that file
and nothing else, exactly as it reads the 2027 one, and `fire(..., year=2026)`
produces **2,012 Mumbai firings from 137 firing rules**.

Every comparison is against the **Mumbai** column. The source computes its own
rise, set and civil day for Mumbai and says so.

## Where a miss came from

The instruction for this run asked for the proportions of three causes: a rule is
unported, a condition is wrong, or the row came from judgement we cannot
reconstruct. The 188 misses fall out as:

| cause | windows | share |
| --- | --- | --- |
| **nobody wrote the rule** (`no_section` + `subtable` + `series_no_rule`) | **131** | 70% |
| **a rule exists and is blocked on a named input** | **48** | 26% |
| **a rule runs and did not fire on this window** | **7** | 4% |
| **the rule is ported and not wired** | **2** | 1% |

**Seven.** The category everyone fears — the assembled layer computing the wrong
answer — is seven windows out of 354, and **six of the seven have an identified
cause**: two are the source's own combust/rise convention, two are a declared
navamsa-resolution limit, and two are source defects where the document's own
Chapter-1 table agrees with us against its Chapter-4 row. The build's gap is
coverage, not correctness.

### The navamsa tie, measured for the first time

`residency/order_in_sign` resolves which body is ahead **at navamsa resolution**
(3°20′), from the emitted ingress series, because no rule may ask the ephemeris for
a longitude. Around a conjunction the pair shares a navamsa for days, the ordering
is tied, and **neither** the "ahead" rule nor the "behind" rule fires. That
limitation was declared when the rules were written — `ORDER_FLAG`, and b079's own
note says a tied stretch "fires neither this rule nor B80".

This run puts a number on it against the document for the first time:

| pair | our behind-window | our ahead-window | the gap | what the source prints in the gap |
| --- | --- | --- | --- | --- |
| Venus / Jupiter | 14-May → 02-Jun | 11-Jun → 04-Jul | **08 → 10-Jun** | *Venus behind Jupiter*, 08 → 10-Jun |
| Mars / Jupiter | 18-Sep → 31-Oct | 20-Nov → 31-Dec | **12 → 19-Nov** | *Mars behind Jupiter* 12 → 16-Nov, *ahead* from 16-Nov |

Both bodies are unambiguously ordered in the gap — Venus enters Cancer 08-Jun,
Jupiter has been there since 01-Jun, and the exact conjunction is 09-Jun 19:59 UTC
— so the source is right and we emit nothing. **Cost: two printed windows, and ten
days across the two pairs.** The declared limitation is real, it is now measured,
and it is not fixed here.

Also visible in the same table: the source prints **no** Venus-behind-Jupiter row
for our 14-May → 02-Jun Gemini co-residency at all. It prints order rows only
around the crossing. That is 20 of our extra days below, and it is a difference in
what the two sides think the rule is about, not a difference about the sky.

### Two further source defects, both of a class already on record

Neither was looked for. Both fell out of a near-miss that had to be explained.

**The 24-Apr Sun-Herschel row carries Venus's date.** The source's own p.34 table
gives *Venus 24-Apr-26 7:29* and *Sun 22-May-26 19:57*; Chapter 4 prints "Sun
Herschel Conjunction" against 24-Apr. Our computed Sun conjunction is 22-May
19:56 IST — **one minute** from the source's own figure, which is what makes the
attribution safe rather than a competing opinion. This is the **B76 shape**: a
right value in a wrong cell, identified by the value rather than by the cell.

**The 20-Nov "Vyatipath Yog on Sunday" row is dated on a Friday.** 20-Nov-2026 is
a Friday; the Vyatipata yoga of that week runs 22-Nov 02:30 → 23-Nov IST, and
22-Nov is the Sunday. The row's date contradicts its own title, which is the
**B106 shape** — a row asterisked by its own condition.

Both are recorded here and neither is yet in `source_defects`; they are findings of
this run, not conclusions of it.

## Where both sides print a verdict

Our verdict text is carried verbatim from the section; the source's is the
inference on the monthly row. Both sides are read for direction by the **same
function**, so neither is read more generously.

| | windows |
| --- | --- |
| **agree** | **105** |
| source states a direction, we print none | 26 |
| neither states a direction | 12 |
| agree, source narrows the scope | 8 |
| **disagree** | **6** |
| one side qualifies with both directions (source) | 3 |
| we state, source defers ("Explained separately") | 3 |
| one side qualifies with both directions (ours) | 2 |
| we state, source states none | 1 |

**105 agree, 8 agree with a narrower scope, 6 disagree.** The 26 where the source
states a direction and we print none are `construction: null` rows — sections that
print no verdict — and they are a correct outcome, not a gap: nothing here infers a
direction the document did not write.

The "qualifies with both directions" row exists because *"Positive, but during a
major negative transit"* is not the opposite of *Bullish*; it is the same direction
with a qualification the other side does not carry. Counting it as a disagreement
would overstate the conflict and counting it as agreement would hide the
qualification, so it is its own row.

### The six disagreements are the document disagreeing with itself

Our verdict is carried verbatim out of the source's own Chapter-1 section. So where
it and a Chapter-4 row differ, **both sides of the disagreement are the
document's**. Measured directly over the printed rows:

> **121 printed rows agree with their own section's verdict. 5 contradict it —
> across 4 of the 62 event names where both sides state a direction.**

| event | its section says | printed rows agreeing | contradicting |
| --- | --- | --- | --- |
| Shani Chandra Dwidwadash Yog | Bearish | 12 | **2** — 04-Jul and 27-Aug, both printed *Positive* |
| Mrigsira on Thursday | Bearish | 4 | **1** — 29-Oct, printed *Positive*, and that row carries **no colour class at all** while every other Mrigsira row is marked `negative` |
| Shukla Pratipada Kshay | Bearish | 0 | **1** — 15-Jun, *Positive* |
| Shukla Trayodashi on Saturday | Bearish | 0 | **1** — 27-Jun, *Positive* |

The sixth disagreement is of a different kind: 10-Apr, where our text is *"Saturn
Combust is usually bearish, specifically in sectors ruled by Saturn"* and the row
reads *"Explained separately (Major Positive Turning)"* — three rise events on one
day, which the chapter reads as a turning rather than as any one section's verdict.

**The monthly calendar carries per-date overrides of its own rules' verdicts.** The
rule layer has no mechanism to represent that and should not acquire one by
inference; it is recorded here as a property of the source. It also bounds how good
a verdict match could ever be: **5 rows in 126 — 4% — are rows where reproducing
the section's verdict correctly means contradicting the calendar.**

## Two records this run is asked to carry

### `vedha_wheel` is a consequence of §12.10, not an independent missing input

`CONFIG_PORT_REPORT.md` lists six inputs blocking the twenty unported configuration
groups, and reports `vedha_wheel` as **"a sixth, found during the port"** — true as
discovery, and misleading as accounting. It is not an input the document withholds.
It is the **downstream cost of a decision this build made**:

> §12.10 withdrew `b134_venus_nakshatra_vedh` and `b132_mars_nakshatra_vedh` because
> Venus's and Mars's Fast/Normal thresholds each crossed **once** in 2026 and so
> were fitted with **zero degrees of freedom**. A number that cannot fail is not
> evidence. Mercury's crossed six times, held, and was kept.

Two configuration groups — `silver-bullish#10` (*Mercury or Jupiter Do Vedh of
Venus*) and `silver-bearish#6` (*Mercury Venus or Moon Venus Mutual Vedh*) — are
blocked on `vedha_wheel` and would be portable today under the withdrawn
thresholds. **Every one of the thirteen printed rows of silver-bearish#6 resolves
exactly through B134's Venus wheel.** The transcription is right; the key is
unearned, which is what §12.10 ruled.

So the cost of the withdrawal is now stateable: **two configuration groups, plus
the four catalogue-B rules §12.10 withdrew, plus the Mars rows this fixture
attributes to b120 and b132.** That cost is correct to pay. It should be visible as
downstream of a decision — with a pointer to §12.10 — so that anyone revisiting the
withdrawal when a second crossing arrives can see both what it bought and what it
cost, rather than finding a sixth missing input and wondering why the document
never supplied it.

### The 34-of-58 counterfactual belongs in §12.16

Recorded in `STEP4_DECISIONS.md` §12.16 as well as in the port report. It is the
first instance in this build where the size of an averted failure was **measured**
rather than described, and every prior instance in that section was caught after
the fact. The guard was built **before** the port and is proven to refuse all three
of its cases, which matters because the standing problem has been guards nobody has
seen fail.
