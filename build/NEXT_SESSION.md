changed no import: `tools/` sits at the same depth `scratch/` did.

### 1d. Bhadra — 54 windows — NEEDS A NEW EVENT CLASS

The only one of the four that changes the astronomy layer, and the largest single
event name in the source's Chapter 4.

* **What to build:** a `karana_ingress` event class in `finastro/events.py` and a
  generator in `build_2027.py`, under Step-3 discipline — computed, bisected to
  the second, never transcribed, carrying the QA fields every other class carries.
* **The arithmetic:** a karana is a **6-degree step of the Moon−Sun elongation**
  (a tithi is 12°, so a karana is half a tithi). **Vishti (Bhadra) falls on karana
  numbers 8, 15, 22, 29, 36, 43, 50 and 57** of the 60-karana lunar month.
* **Certainty A**, on the tithi's own ground: elongation is a **difference** of
  longitudes, so the ayanamsha subtracts from both terms and cancels. Already
  established and measured for the tithi series — identical to the second under
  Lahiri, Krishnamurti, Raman, Fagan-Bradley and tropical. Do **not** grade it B.
* **Ground truth already in hand:** the Bhadra section (pp.120–124) prints **16
  boundaries**, and the engine reproduced them **within 25 seconds** during G-7 —
  eight of them are also tithi boundaries, which is how the agreement was
  measured. Verify against those 16 before porting the rule.
* **Known source defect to carry** (do not "fix" it silently, and do not let it
  fail the verification): the **monthly table's 13-Jan cell reads `3:59`** where
  the correct value is **`02:00:05`**. The Bhadra section itself prints 02:00, so
  the section is right and the January calendar is ~1h59m late. This is the
  `source_defects` class README already describes; add it there with its
  verification method.
* **Requires regenerating BOTH years**: `python build_2027.py` and
  `python tools/build_2026.py`. The 2026 file is what the fixture reads, so the
  fixture cannot see Bhadra until 2026 is regenerated.

## TASK 4 — the span-vs-daily render proposal (report, do not implement)

Asked for and not delivered this session. The shape, so it can be picked up cold:

* **The finding:** of 413 extra Mumbai days the fixture attributes to rules the
  source also prints, **251 come from nine combust windows** — and those nine are
  **9 runs**, not 251 events. Mars is combust 01-Jan → 10-Apr 2026 (100 days);
  Mercury's seven windows total 144 days.
* **The mismatch:** the rule layer emits **one row per civil day a state holds**.
  The source treats a combust span as **one row with two boundaries** (start date,
  end date), and its own Duration column confirms it — 33 for Mercury combust
  02-Jan → rise 04-Feb.
* **What to decide:** how a months-long *state* should render against a *dated
  event*. The obvious candidates are (i) collapse a state to one row with
  start/end, (ii) keep daily rows but mark the boundary days, (iii) emit both and
  let the consumer filter on a `row_kind` field.
* **What the proposal must state:** the row count under it. Any collapse changes
  the calendar's headline figure, which currently appears in README, the status
  page and the HTML panel — so the number and every page quoting it move together.

## Standing constraints for whoever picks this up

* **Nothing is typed twice.** Every value is computed once into a canonical record;
  JSON, HTML and CSV all render from it.
* **A rule reads the generated calendar, never the ephemeris** — so a rule and the
  calendar cannot disagree about the sky.
* **Verdict text is the source's own words or it is null.** No derived verdict, and
  `confidence` is `untested` on every row, with no code path that raises it.
* **A missing input is named on the rule**, not approximated.
* Financial astrology is a speculative interpretive framework. Nothing this project
  produces is a forecast or investment advice.
